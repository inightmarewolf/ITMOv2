# Отчёт 1. Атаки / находки на исходный сервис

Смотрел `lab/service.py` до правок + гонял гипотезы через `Shop.dispatch` (без выхода за localhost). Модель угроз — в `threat-model.md`.

Ниже — что реально всплыло. «Атака» = учебная проверка на своём процессе Mini Shop.

## T1. SQL injection в profile / search / assistant context

В исходнике id и q клеились в SQL строкой. Достаточно кривого `id`, чтобы сломать запрос или вытащить лишнее.  
Проверка сейчас зафиксирована тестом `test_sql_injection_profile_id_safe` (ожидаем безопасный отказ, не «все строки»).

## T2. IDOR профилей, заказов, файлов

- `/profile?id=2` под токеном alice отдавал чужой профиль — без сверки с сессией.
- `/orders` без фильтра отдавал заказы всех.
- `/files?user=bob&...` читал чужой чек без проверки владельца.

Это прямая утечка учебных ПДн/чеков между клиентами.

## T3. Подмена роли через `X-Role`

`/admin/export` смотрел на заголовок, а не на `sessions[token].role`. Клиент с обычным логином и `X-Role: staff` получал выгрузку профилей.

## T4. Подмена цены заказа

`POST /orders` брал `body["price"]`, если поле было. Можно было купить `lamp` за `1` вместо каталожных `1500`.

## T5. Открытые debug-логи

`GET /debug/logs` без auth. В лог писались body/headers как есть → утекали пароли с `/login` и токены.

## T6. Stored XSS в отзывах

Текст отзыва вставлялся в HTML как есть. Поле `text` с тегом script попадало в `/reviews/view` живым.

## T7–T8. Assistant: опасные tools + слабый контроль

- В prompt клиенту светились `export_profiles` и `delete_tree`.
- `/assistant/execute` исполнял decision почти без ACL: чужой `read_file`, удаление дерева fixture, выгрузка профилей.
- Отзывы и question попадали в context целиком → классический prompt-injection вектор на planner (даже если модель «хорошая», сервер обязан резать execute).

Отдельно прогнал принудительный decision с `delete_tree` / `export_profiles` / чужим чеком — до фикса сервер это принимал. Это как раз «серверная» проверка из README, не зависящая от послушания LLM.

## Итог до фикса

Функциональные тесты курса зелёные и на дырявом коде — они контракт «магазин работает», а не security. Поэтому добавил `lab/test_security.py` под ожидаемое безопасное поведение и уже по нему чинил.
