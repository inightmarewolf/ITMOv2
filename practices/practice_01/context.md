## Context Pack для первого рабочего сценария

### Факты и правила

- Помощник анализирует один PR и возвращает краткое описание изменения, не больше трёх рисков, список проверок ([README.md](README.md), раздел «Задача помощника»)
- Риск должен содержать: файл, строку и доказательство из diff ([README.md](README.md), раздел «Примеры комментария»)
- Решение всегда принимает человек. Помощник НЕ может approve, merge или менять код ([README.md](README.md), раздел «Задача помощника»)
- Входной diff содержит изменения в формате unified diff (пример: [TRAINING_PR.diff](TRAINING_PR.diff))

### Формат входа и результата

- **Вход:** diff одного PR в формате unified diff
- **Результат:**
  1. Краткое описание изменения (1-2 предложения)
  2. Не больше трёх рисков, каждый содержит: файл, строку, описание проблемы и доказательство из diff
  3. Список проверок, которые стоит запустить (команды или сценарии)
- **Формат риска (хороший пример):** `app/api.py, create_review — обращение payload["diff"] вызывает KeyError, если в теле запроса нет поля diff. Проверка: отправить POST /api/reviews с пустым JSON-объектом и проверить ответ сервиса.` ([README.md](README.md), раздел «Примеры комментария»)

### Ограничения и запрещённые действия

- Помощник НЕ может approve или merge PR
- Помощник НЕ может менять код
- Помощник НЕ должен давать общие советы без ссылки на конкретный файл и строку
- Помощник НЕ должен превышать лимит три риска
- Решение всегда принимает человек ([README.md](README.md), раздел «Задача помощника»)

### Хороший пример

```text
app/api.py, create_review — обращение payload["diff"] вызывает KeyError,
если в теле запроса нет поля diff. Проверка: отправить POST /api/reviews
с пустым JSON-объектом и проверить ответ сервиса.
```

Источник: [README.md](README.md), раздел «Примеры комментария»

### Плохой пример

```text
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

Проблемы: нет ссылки на файл и строку, нет доказательства из diff, нет конкретной проверки.

Источник: [README.md](README.md), раздел «Примеры комментария»

### Что пока неизвестно

- Какие категории рисков приоритетны (security, performance, correctness)?
- Какие проверки считаются достаточными (unit-тесты, integration, manual)?
- Нужно ли оценивать severity рисков?
- Какой язык программирования и фреймворки используются в целевых проектах? (в учебном кейсе — Python + FastAPI)
