# Проблема и метрики

Файл ведёт OpenCode. Обсудите с агентом содержание и проверьте предложенный diff. Все дополнения и исправления поручайте агенту в чате.

## Проблема

- Пользователь: Ревьюеры кода в командах разработки
- Ситуация: При ревью pull request ревьюер вручную ищет типичные проблемы (отсутствие валидации входов, обработки ошибок, небезопасный код)
- Что происходит сейчас: Ревьюер тратит время на поиск очевидных ошибок, которые можно обнаружить автоматически; высокая когнитивная нагрузка; риск пропустить проблему при усталости или большом объёме изменений
- Почему это мешает пользователю или бизнесу: Увеличивается время code review, снижается пропускная способность команды, ревьюеры устают от рутины, возрастает риск пропустить критичные баги в продакшен
- Что не входит в задачу: Автоматическое исправление кода, approve/merge PR, замена человека-ревьюера; принятие решения всегда остаётся за человеком (источник: [README.md](README.md), раздел «Задача помощника»)

## Метрики

Обсудите с OpenCode показатели, по которым можно проверить решение проблемы. Агент записывает согласованный способ замера и ожидаемое изменение для каждого показателя.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Среднее время ревью одного PR (минуты) | Baseline: измерить среднее время между открытием PR и первым комментарием ревьюера за неделю | Снижение на 20-30% | Еженедельно после внедрения помощника | GitHub API / GitLab API: время между created_at PR и первым review comment |
| Доля PR с найденными критичными проблемами после деплоя (%) | Baseline: доля PR, для которых в течение 7 дней после merge создан hotfix или bug-отчёт | Снижение на 15-25% | Ежемесячно | Issue tracker: связь между PR и bug-отчётами/hotfix, метки "critical", "production" |
| Количество найденных проблем на 1 PR (штук) | Baseline: среднее число комментариев ревьюера с меткой "bug" или "issue" за неделю | Рост на 10-15% за счёт помощника | Еженедельно | GitHub/GitLab API: количество review comments с метками bug/issue |

## Почему изменение метрики подтвердит решение проблемы

1. **Снижение времени ревью:** Если помощник находит очевидные проблемы автоматически, ревьюер тратит меньше времени на их поиск и может быстрее дать первый фидбек.
2. **Снижение доли критичных проблем после деплоя:** Если помощник находит риски (например, отсутствие валидации или обработки ошибок), которые ревьюер мог пропустить, меньше багов доходит до продакшена.
3. **Рост количества найденных проблем на PR:** Помощник дополняет ревьюера, находит проблемы, которые человек мог упустить из-за усталости или объёма изменений. Рост метрики означает, что помощник эффективен.

Важно: решение считается успешным только при сохранении качества финальных комментариев ревьюера (не должно быть ложных срабатываний, снижающих доверие к помощнику).
