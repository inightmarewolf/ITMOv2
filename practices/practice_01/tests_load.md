# Нагрузочные проверки

Файл ведёт OpenCode. Обсудите с агентом содержание и проверьте предложенный diff. Все дополнения и исправления поручайте агенту в чате.

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Подтверждение |
|---|---|---|---|---|
| Пиковая нагрузка: одновременные запросы от многих PR | 50 одновременных POST /api/reviews с diff ~10KB, длительность 5 минут | Latency p95 ≤ 2 секунды (без учёта LLM), успешность ≥ 99%, без падения сервиса | Latency (p50, p95, p99), throughput (requests/sec), error rate, CPU/memory usage | Load-тест с k6 или Locust: `k6 run --vus 50 --duration 5m load_test.js` |
| Длительная нагрузка: проверка утечек памяти | 10 одновременных запросов, длительность 1 час | Memory usage не растёт >10% за час, нет memory leaks | Memory usage (RSS), CPU usage, количество успешных запросов | Load-тест + мониторинг: Prometheus + Grafana, проверка метрики `process_resident_memory_bytes` |

**Почему нагрузочное тестирование нужно:**
Для MVP (инкремент 2, [project_management.md](project_management.md)) нагрузочное тестирование не критично, так как сервис используется одной командой (~10 разработчиков, ~20 PR/день). Однако для production deployment (инкремент 3+) нагрузочное тестирование обязательно, чтобы:
- Проверить поведение при пиковой нагрузке (например, после mass merge в релизную ветку)
- Выявить узкие места (LLM API rate limits, database bottlenecks, если добавим кеширование)
- Настроить auto-scaling и rate limiting ([adr.md](adr.md): 10 запросов/минуту)

**Условие, при котором понадобится:**
Когда количество PR вырастет до >100/день или сервис будет использоваться несколькими командами (>50 разработчиков). Тогда потребуется:
- Horizontal scaling (multiple API instances за load balancer)
- Кеширование повторных запросов (если один diff анализируется дважды)
- Мониторинг стоимости LLM-запросов и оптимизация промпта (снижение input tokens)

- Тип промпта: zero-shot (агент OpenCode в режиме Build)
- Строка в [`prompts.md`](prompts.md): (домашняя работа, не отдельный запуск)
- Что проверил студент и какие исправления поручил агенту: Проверить согласованность с adr.md (rate limiting, масштабирование), project_management.md (инкременты, MVP vs production); убедиться что допустимые пределы реалистичны (p95 latency, error rate); проверить что обоснована необходимость load-тестов для production и их отсутствие для MVP
